## 2. P1 问题（建议优先修复）

### P1-1 `BleTask_SendTag()` 把打标类型压成 0/1

**现象**
自动停车时串口打印的是两条 `[T] OK`，而 `[RACE] det` / `[RACE] stop` 一次都不出现。

**证据**

```c
/* USER/Src/Ble_task.c:1034 */
uint8_t BleTask_SendTag(uint8_t ok)
{
    uint8_t item = (ok != 0U) ? 1U : 0U;   /* ← 2/3 被压成 1 */
    ...
    return (xQueueSend(s_tag_queue, &item, 0U) == pdTRUE) ? 1U : 0U;
}
```

消费端却按 2/3 分支处理：

```c
/* USER/Src/Ble_task.c:829-845 */
if (tag == 2U)      { BleTask_Print("[RACE] det ..."); }
else if (tag == 3U) { BleTask_Print("[RACE] stop ..."); }
else                { s_tag_seq++; BleTask_Print("[T] %s #%u ...", tag ? "OK" : "FAIL", ...); }
```

调用端确实传入了 2/3：

- `USER/Src/Control_task.c:329` → `BleTask_SendTag(2U)`（识别到启停线）
- `USER/Src/Control_task.c:342` → `BleTask_SendTag(3U)`（已到位）
- `USER/Src/Control_task.c:558` → `(1U)`（长按 KEY3 = OK）
- `USER/Src/Control_task.c:579` → `(0U)`（短按 KEY1 = FAIL）

**根因**
队列元素类型是 `uint8_t`，写入前多做了一次"归一化"，把协议值 2/3 当成了布尔真值。

**影响**
1. 每次自动停车会向日志插入 **2 条假的 `[T] OK`**，`s_tag_seq` 也被多计 2；
2. 按 `[T]` 切段的整套分析流程（`tools/tag_report.py`）会把一次跑圈拆成 3 段，里程/误差统计全错；
3. 自动停车是否真的识别到了启停线，在日志上完全不可见——这正是你排查 `ct` 版"完全不停车"时最需要的信息。

**修复**

```c
uint8_t BleTask_SendTag(uint8_t ok)
{
    uint8_t item = ok;     /* 0=FAIL 1=OK 2=[RACE]det 3=[RACE]stop，原样透传 */
```

**验收**
自动停车后日志应出现 `[RACE] det d<cm> lrn0 t<ms>` 与 `[RACE] stop t<ms>`，且 `tag_report.py` 的标记数不再多算。

### P1-2 `BLE_STATE`(PA1) 被配成推挽输出并拉低 —— 连接状态检测失效

**现象**
蓝牙连上后永远打不出 `[BLE] connected (times=N)` 和版本横幅（`[VER] ...`），LED2 一直慢闪"未连接"。

**证据**

```c
/* Core/Src/main.c:799 */
HAL_GPIO_WritePin(GPIOA, BLE_STATE_Pin|M_STBY_Pin, GPIO_PIN_RESET);

/* Core/Src/main.c:808-811 */
/*Configure GPIO pins : BLE_STATE_Pin M_STBY_Pin */
GPIO_InitStruct.Pin  = BLE_STATE_Pin|M_STBY_Pin;
GPIO_InitStruct.Mode = GPIO_MODE_OUTPUT_PP;
```

- `.ioc` 同样声明为输出：`linefllowing_car.ioc:126` → `PA1.Signal=GPIO_Output`
- 连接判据：`Drivers/BSD/Inc/Ble.h:69` → `#define BLE_STATE_CONNECTED GPIO_PIN_SET`
- 读取处：`Drivers/BSD/Src/Ble.c:195` → `HAL_GPIO_ReadPin(...) == BLE_STATE_CONNECTED`
- `BLE_Init()`（`Ble.c:165`）**没有任何** GPIO 重配置

**根因**
CubeMX 把 HC-05 的 STATE 引脚误配成输出；`HAL_GPIO_ReadPin` 读的是 `IDR`，引脚被 MCU 推挽拉低后读数取决于与模块输出的对顶结果，表现为基本恒 0。

**影响**
1. `BLE_IsConnected()` 基本恒为假 → 连接/断开事件逻辑（`Ble_task.c:955-990`）整段是死代码；
2. 你注释里明确写的"每次连上都打印版本"永不触发，回到最怕的"不知道烧的是哪一版"；
3. `BLE_UpdateLed()` 永远走"未连接慢闪"分支，LED2 指示失去意义；
4. **硬件风险**：MCU 推挽输出与模块的 STATE 输出直接对顶，有灌电流/长期损伤风险。

**修复**

```c
/* Core/Src/main.c MX_GPIO_Init：把 PA1 从输出组摘出来，单独配成输入 */
GPIO_InitStruct.Pin  = BLE_STATE_Pin;
GPIO_InitStruct.Mode = GPIO_MODE_INPUT;
GPIO_InitStruct.Pull = GPIO_NOPULL;      /* HC-05 STATE 由模块自己驱动 */
HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);
```

同时把 `.ioc` 里 `PA1.Signal` 改为 `GPIO_Input`（否则 CubeMX 重新生成会把代码改回去）。
保险做法：在 `BLE_Init()` 里再独立配一次，让驱动本身不依赖 CubeMX 生成结果。

**验收**
手机连上后串口应出现 `[BLE] connected (times=1)` 与 `[VER] line-follower cv ...`；LED2 由慢闪变常亮。

### P1-3 灰度传感器掉线检测从未生效

**现象**
拔掉灰度传感器、或总线被从机拉死时，`[G]` 行的 `e=0/N` 始终不变，车按最后一帧数据继续满速直行。

**证据**

`Gray_Update()` 中唯一一处对 `fail_count` 的写入是清零：

```c
/* Drivers/BSD/Src/Gray.c:390-395 */
/* 通信成功，清除失败计数 */
sensor->fail_count  = 0U;
```

全文件再无 `fail_count++`，`sensor->total_fails` 也从未累加（`[G] ... e=%lu/%lu` 永远打印 `0/N`）。
而控制侧的保护判断是：

```c
/* Drivers/BSD/Src/LinePD.c:300-304 */
if (gray->fail_count >= GRAY_FAIL_LIMIT)
{
    pd->line_lost = 1U;
    return LINE_PD_ERR_I2C;      /* 永不触发 */
}
```

**根因**
`ch`/`ci` 之后采样改成 DMA 异步，`Gray_Update()` 变成"只消费已完成的帧"，原来阻塞读失败时的计数逻辑被一并删掉，但没有在新路径补回。

**影响**
传感器失效时 `s_ready` 永远为 0，`Gray_Update()` 在 `Gray.c:381-384` 直接早退，`position_mm` 冻结在最后一帧 —— 外环看到的是"线在中间"，会一直按基础速度直冲，直到撞墙或跑出赛道。这是当前最危险的失效模式。

**修复**

```c
/* Gray.c，s_ready == 0 分支：连续无新帧要计失败 */
if (s_ready == 0U)
{
    if (sensor->fail_count < 0xFFFFU) { sensor->fail_count++; }
    sensor->total_fails++;
    return 1U;
}

/* 正常消费帧后（原清零处保持不变） */
sensor->fail_count = 0U;
```

并在 `Gray_StartSample()` 的两条失败路径上同样计数：

```c
/* 1) 看门狗超时复位外设 */
(void)HAL_I2C_DeInit(hi2c); (void)HAL_I2C_Init(hi2c);
s_busy = 0U;
if (g_gray.fail_count < 0xFFFFU) { g_gray.fail_count++; } g_gray.total_fails++;

/* 2) 发起 DMA 失败 */
if (HAL_I2C_Mem_Read_DMA(...) != HAL_OK)
{
    s_busy = 0U;
    if (g_gray.fail_count < 0xFFFFU) { g_gray.fail_count++; } g_gray.total_fails++;
}
```

> 建议 `GRAY_FAIL_LIMIT` 保持 10（= 50ms 无有效帧）——5ms 采样下正常抖动最多丢 1~2 拍。

**验收**
拔掉传感器后 50ms 内 `LinePD_Update()` 应返回 `LINE_PD_ERR_I2C`，`[L]` 行 `sc` 变 `NONE`，`[G]` 行 `e` 开始增长。

### P1-4 `LAP` 步长 50 与"10 = 自适应"语义冲突

**现象**
OLED 上 LAP 默认显示 10（自适应），此时按一下 KEY2 变成 60，按一下 KEY1 直接变 0（关闭）—— **自适应档再也选不回来**。

**证据**

```c
/* USER/Src/Oled_task.c:142-149 */
 * LAP: 比赛自动停车用的一圈周长，单位 cm（步长 10cm）。
 *   0      = 关闭自动停车
 *   10~40  = 自适应模式 ...
{ "LAP",    50.00f,   0.00f, 3000.00f },   /* ← 实际步长 50 */
```

分档语义在别处：

```c
/* USER/Src/Control_task.c:66 */
volatile float g_race_lap_cm = 10.0f;       /* 10 = 自适应（<50 都是自适应） */

/* Drivers/BSD/Src/LinePD.c:2036 */
else if (lap_cm < 50.0f) { pd->race_enabled = 1U; pd->race_lap_cm = 0.0f; }  /* 自适应 */
```

**根因**
`cr` 提交把步长从 10 改成 50（为了一次性调大周长），但"`<50` = 自适应"的分档没有同步调整，注释也留在 10cm。

**影响**
1. 自适应档（10~49）在 UI 上不可达；
2. 若真按到 50：`arm = 50×0.8 = 40cm`、识别窗口 `[50−17±25] = [8,58]cm`，车跑 ~33cm 就会判"到位"并硬刹——比"不停车"更糟，会让人误判成"识别很灵"。

**修复**

```c
{ "LAP",    10.00f,   0.00f, 3000.00f },   /* 恢复 10cm 步长，与 <50 分档一致 */
```

若确实想保留大步长，可改为"分段步长"：`值 < 50 时步长 10，≥ 50 时步长 50`。

**验收**
从 10 按 KEY1 → 0；再按 KEY2 → 10（回到自适应）。`[P] ... lap10.0 arm0.0` 应保持不变。

## 3. P2 问题

### P2-5 控制任务直接抢 USART2，`[PD]` 日志大量丢行

**证据**

```c
/* Drivers/BSD/Src/LinePD.c:1681  （丢线停车） */
(void)HAL_UART_Transmit(&huart2, (uint8_t *)msg, (uint16_t)strlen(msg), 40U);

/* Drivers/BSD/Src/LinePD.c:1733  （搜索找回） */
(void)HAL_UART_Transmit(&huart2, (uint8_t *)msg, (uint16_t)len, 40U);
```

`HAL_UART_Transmit()` 在 `huart->gState != HAL_UART_STATE_READY` 时**立即返回 `HAL_BUSY`**，参数里的 40ms 超时根本用不上。

**根因**
串口打印没有统一走蓝牙任务的队列（这一点项目自己的约定里已经写明，但 LinePD 这段漏改）。

**影响**
实测最忙 60s 串口占用 83%，控制任务抢占发送时大概率撞上 BUSY → `[PD] lost` / `[PD] ok` 整行丢失。而这两行正是判断"搜索用了多少角度、方向对不对"的唯一依据。

**修复**
复用已有的打标队列模式，新增一个轻量消息队列：

```c
/* Ble_task.h */
typedef enum { BLE_MSG_PD_LOST = 0, BLE_MSG_PD_OK = 1 } Ble_Msg;
uint8_t BleTask_SendPdEvent(uint8_t kind, int16_t turn_deg);   /* 只入队，不阻塞 */
```

控制任务侧改成 `BleTask_SendPdEvent(BLE_MSG_PD_OK, (int16_t)pd->last_commit_turn);`，由蓝牙任务统一打印。

**验收**
一次完整跑圈中 `[PD] ok` 的数量应与实际搜索次数一致。

### P2-6 `recover_count` 永不复位 —— "连续 4 拍确认找回"只在上电后第一次有效

**证据**

```c
/* LinePD.c:1711-1714  只自增，不判断是否曾丢线 */
if (pd->recover_count < 0xFFU) { pd->recover_count++; }
if (pd->recover_count >= LINE_RECOVER_CYCLES) { ... reset search state ... }

/* LinePD.c:1740  把它钉在阈值上 */
pd->recover_count = LINE_RECOVER_CYCLES;
```

复位点只有 `LinePD_Reset`（`LinePD.c:177`）与承诺转向分支（`LinePD.c:1040`），**第 3 步"丢线计数"里没有清零**。

**根因**
`recover_count` 的语义是"连续看到线的拍数"，但丢线时没有把它重新置 0，于是第一次恢复后它就饱和在 4。

**影响**
第一次搜索成功后，之后任何一次搜索只要**出现一帧线**就立刻结束搜索。锐角弯过冲时"瞥见回来那条腿一帧"就会退出搜索并沿旧线往回跑 —— 正是注释里描述过的历史故障，会在跑了几圈之后复现。

**修复**

```c
/* ---------- 3. 丢线计数 ---------- */
if (Gray_IsLineLost(gray) != 0U)
{
    if (pd->lost_count < 0xFFU) { pd->lost_count++; }
    pd->recover_count = 0U;              /* ← 新增：重新从 0 计数 */
}
else
{
    pd->lost_count = 0U;
}
```

**验收**
锐角弯搜索中即使某一拍看到线，也要连续 4 拍（80ms）才打印 `[PD] ok`。

### P2-7 DMA 化之后两个自检函数彻底失效

**证据**

`Gray_Update()` 现在只消费 DMA 帧：

```c
/* Gray.c:381-384 */
if (s_ready == 0U) { return 1U; }      /* 无新帧 */
```

但自检函数只调 `Gray_Update()`，从不调 `Gray_StartSample()`：

- `Drivers/BSD/Src/Gray.c` `Gray_TestSequence()` 循环体（约 1080 行）
- `Drivers/BSD/Src/LinePD.c:1823` `gray_result = Gray_Update(gray, hi2c);`

**影响**
`Gray_TestSequence()` 与 `LinePD_VerifySigns()` 在没有任何采样发起的情况下必然返回 1 → 全部打印 `I2C FAIL`。而 README/头文件明确要求"上车跑圈之前必须先跑 `LinePD_VerifySigns()` 把三个符号钉死"——这条安全流程现在是失效的。

**修复**

```c
/* 自检里改成"发起 + 等一帧" */
Gray_StartSample(hi2c);
HAL_Delay(2);                    /* 17 字节 @400kHz ≈ 0.4ms，给 2ms 足够 */
gray_result = Gray_Update(gray, hi2c);
```

或在 `Gray.c` 里保留一个阻塞版 `Gray_ReadBlocking()` 专供自检使用。

**验收**
`LinePD_VerifySigns()` 的第 1 段应能正常打印 `pos/error/verdict`，而不是整屏 `I2C FAIL`。

### P2-8 `Encoder_UpdateSpeed()` 在 5ms 循环里被无条件调用 —— 速度反馈噪声 ×4

**证据**

```c
/* USER/Src/Control_task.c:198  每 5ms 无条件调用 */
Encoder_UpdateSpeed();
```

而驱动的设计前提是 20ms：

```c
/* Drivers/BSD/Inc/Encoder.h:303 */
* 调用节奏很关键：必须固定按 ENCODER_PERIOD_MS(20ms) 的周期调用，
* 且两次调用之间的时间就是速度的积分窗口。
```

量化计算（`ENCODER_WHEEL_DIAMETER_MM=48`、`PPR=13`、`EDGE=4`、`GEAR=25`、`CAL=0.97`）：

| 采样窗口 | 1 个计数对应的速度 | 低通时间常数（α=0.5） |
| --- | --- | --- |
| 20 ms（设计值） | 0.56 cm/s | ≈ 29 ms |
| **5 ms（实际）** | **2.25 cm/s** | **≈ 7 ms** |

**影响**
送进速度环的 `m` 量化台阶粗 4 倍、滤波时间常数短 4 倍，实测噪声显著增大。这是"主循环提到 5ms 之后车变抖"的一个**独立成因**，与灰度采样率无关（`cn` 提交只换算灰度侧常量）。

**修复（二选一）**

```c
/* 方案 A（推荐）：回到 20ms 采样，与设计一致 */
now = xTaskGetTickCount();
if ((now - last_enc) >= pdMS_TO_TICKS(ENCODER_PERIOD_MS))
{
    last_enc = now;
    Encoder_UpdateSpeed();
}

/* 方案 B：保持 5ms，把滤波系数按周期换算，抵消噪声 */
#define ENCODER_SPEED_FILTER_5MS   0.159f    /* 1 - (1-0.5)^(5/20) */
```

**验收**
静止时 `[A]/[B]` 的 `m` 抖动幅度应明显下降；同样 LKP/LKD 下直道不再高频修正。

### P2-9 MPU6050 掉线重试在控制环里做 `HAL_Delay`

**证据**

```c
/* USER/Src/Control_task.c:226-240 */
if (MPU6050_IsReady() == 0U)
{
    if ((HAL_GetTick() - s_mpu_retry_tick) >= 3000U)          /* 每 3 秒 */
    {
        s_mpu_retry_tick = HAL_GetTick();
        if (MPU6050_Init(&hi2c2) != 0U)                       /* 内部 HAL_Delay(30)+HAL_Delay(60) */
        {
            if (g_ctrl_mode == CTRL_MODE_STOP) { MPU6050_Calibrate(100U); }   /* 100×2ms = 200ms */
        }
    }
}
```

`MPU6050_Init()` 内部：`HAL_Delay(30)`（`MPU6050.c:157`）+ 探测 + `HAL_Delay(60)`（`MPU6050.c:189`）。

**影响**
没装或损坏 IMU 时，循迹中**每 3 秒控制环停摆 ~100ms**（STOP 模式下 ~300ms）。这期间 PWM 保持上一拍占空比（硬件继续驱动电机），而速度/姿态反馈全部停止 —— 正好发生在需要及时响应启停线的时刻。

**修复**
- 把重试整体搬到蓝牙任务（或新建低优先级诊断任务），控制任务只读 `MPU6050_IsReady()`；
- 或最低限度：`HAL_Delay` 改 `vTaskDelay`，且仅在 `CTRL_MODE_STOP` 下做初始化与标定。

**验收**
拔掉 IMU 跑车，`[L]` 行间隔应保持稳定（不出现 100ms 以上的空洞）。

### P2-11 `BleTask_Print()` 截断时按返回值发送 —— 栈越界读

**证据**

```c
/* USER/Src/Ble_task.c:190-196 */
len = vsnprintf(buf, sizeof(buf), fmt, args);
if (len > 0)
{
    (void)HAL_UART_Transmit(&huart2, (uint8_t *)buf, (uint16_t)len, BLE_TX_TIMEOUT_MS);
}
```

C99 规定 `vsnprintf` 返回"**本该写入**的长度"，发生截断时该值大于缓冲区大小。

**影响**
一旦某条日志超过 192 字节，会从 192 字节的栈缓冲区外读取多余字节发送，可能泄露栈内容甚至触发总线错误。当前所有调用点都较短，属潜伏缺陷。

**修复**

```c
if (len >= (int)sizeof(buf)) { len = (int)sizeof(buf) - 1; }   /* 截断即封顶 */
```
